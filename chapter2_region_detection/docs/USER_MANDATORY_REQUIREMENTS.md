## 二、12 条强制要求（编号 0–11）

### 0. 实验任务必须先设计，再由 Luna 极高执行

主窗口派发任何实验任务时，必须提供详细的任务目标、方案、详细设计、执行步骤和
验收标准。实验运行子代理使用 `gpt-5.6-luna`、`xhigh` 推理强度。所有产出和结论由
主窗口审核后才能进入下一阶段或成为正式结果。

### 1. 子窗口禁止删除或重置

主窗口以外的任何窗口或子代理不得删除、重置、清理、回滚或覆盖文件，不得执行
`git reset`、`git clean`、破坏性 checkout/restore 或等价操作。这类操作必须由主窗口
先核对绝对路径、进程、目录内容和恢复价值，再决定是否执行。子代理遇到此类需要时
只能保留证据并上报。

### 2. 启动核验每 15 分钟执行一次

实验启动与运行核验使用一个固定、独立、专用的只读窗口/子代理，模型为 `gpt-5.6-luna`、
`high` 推理强度，每 15 分钟检查一次。检查实验是否已启动、是否中断、是否有异常、是否存在重复 writer、
输出是否增长以及身份/seed/hash 是否漂移。正常且无实质变化时保持安静；发现完成或
中断、失败或其他异常时停止本次监控并报告主窗口，由主窗口审核处理和安排下一任务。核验代理不得启动、停止、修复、
复制或清理实验。核验必须使用一个与主窗口分离的单一专用 heartbeat/窗口按时轮询，不得每次
轮询创建新的任务窗口；它只在完成或异常时把证据交给主窗口。旧核验窗口在不再承担运行职责后可以归档，但不得删除历史。

### 3. 全速执行并以三天为冲刺目标

实验应全速推进；能安全并行就并行，能在不改变论文协议和结果的前提下加速就加速，
以三天内给出最终任务结果为冲刺目标。不得用缩短 episodes/ticks、减少 repeats、复用
不应复用的 checkpoint、降低门禁或使用 smoke 数字来伪造“提速”。

### 4. 运行中持续使用 Luna 高监控进度

长实验运行期间使用 `gpt-5.6-luna`、`high` 推理强度的只读监控子代理检查进度。
监控发现某个实验完成或异常时立即向主窗口汇报；主窗口审核结果、备份有用产出，
再按照任务书安排下一任务。监控频率服从第 2 条，不进行高频无变化轮询，也不得为每次
监控创建新的独立任务窗口。

### 5. 所有有用实验产出必须备份

任何可恢复 checkpoint、完整 repeat、正式 episode milestone、冻结依赖、重建资产或
其他有用产出，都必须建立不可覆盖的哈希备份，防止意外清除。备份必须区分 partial、
verified dependency 与 paper-eligible result；备份本身不能把 partial 结果提升为论文结果。
备份后应核验文件数、字节数、manifest 和逐文件 SHA256。

### 6. 节省 token

在不影响实验完整性、正确性和最终结果的前提下节省 token。正常监控保持静默；状态
汇报使用短证据；避免重复读取大文件、重复解释已确认事实和无意义高频轮询。不得通过
省略门禁、测试、备份或主窗口审核来节省 token。

### 7. 能恢复则恢复，不能恢复立即重跑

事故或丢失发生后，先按文件内容、解析结果、SHA256 和 provenance 判断能否恢复，不能
只看文件名或大小。可恢复的资产立即恢复并备份；无法恢复、存在 NUL/截断/哈希漂移或
缺失关键 sidecar 的资产立即按正式协议重跑，并采用安全并行和恢复点加速。不得把损坏
恢复文件作为正式结果，也不得为了避免重跑而降低标准。

### 8. 派发前先确认最终目标、任务书和计划

安排每个任务前，主窗口必须先明确最终目标，重新核对当前任务书、正式交接文档、冻结
manifest 和当前证据，再形成计划、详细设计、资源方案、风险控制和验收标准，然后才
能派发。不得先启动后补设计，不得让子代理自行猜测论文口径或缺失参数。

### 9. 优先保证自有方案效果；对比方案以正确为准

方案设计、GPU 时间、调优、诊断和消融资源优先用于保证 LWM-RL 效果好、主张成立且
结果稳健。对比方案必须没有实现错误、数据泄漏、协议不公平或审计问题，但不要求追求
其最佳效果；按冻结论文适配和公平预算运行即可，禁止为对比方法额外调参、扩大预算或
反复重跑挑选更好数字。

### 10. 充分使用 CPU、GPU 和显存安全并发

必须充分使用可用 CPU、GPU 和显存，尽可能并发执行互不冲突的训练、评测、资产重建、
门检和备份任务，提高产出效率。并发前必须检查显存、系统内存、CPU 竞争、输出目录、
唯一 writer 和恢复点；不得盲目超售资源导致 OOM、无日志退出或重跑。资源调度优先级为：

1. 自有 LWM-RL、Table 2/3 的关键 GPU 训练与调优；
2. 不抢占主方法资源的 CPU-only TERLA/PriorRL/CARL 训练；
3. 已有安全恢复点的 RSMBRL/UAMCTS 等对比评测；
4. 只读门检、聚合、绘图和备份与训练并行执行。

### 11. 上下文压缩前必须生成阶段交接 MD

在主窗口上下文即将压缩、切换对话、应用重启或需要由新代理接管前，必须先生成或更新
一个 Markdown 阶段交接文档，完整总结本段上下文已经完成的工作，供下一次接管继续执行。
不得只依赖聊天摘要、临时终端输出或代理记忆完成交接。

阶段交接文档至少必须记录：

1. 本阶段核对过的最终目标、任务书版本、冻结协议和强制要求文档 SHA256；
2. 已完成工作及其验收结论，明确区分代码完成、依赖完成、partial 与 paper-eligible；
3. 当前运行中的实验、唯一 writer、PID、代码 commit、环境、输出目录、seed、阶段和最近进度；
4. 已产生的有用资产、原始产物、checkpoint、manifest、逐文件 SHA256 和不可覆盖备份路径；
5. 失败、异常、恢复尝试、保留证据、当前阻塞及禁止误用的旧产物；
6. Git 主仓库和各工作树的 HEAD、clean/dirty 状态及未提交改动归属；
7. 尚未完成的表格、图、repeats、门禁与当前最终任务完成度；
8. 下一接管窗口应执行的精确顺序、命令或入口、资源调度、风险控制和验收标准；
9. 所有活跃子任务/监控任务的模型、职责、频率、状态以及需要继续、停止或改派的条件。

交接文档必须写入仓库 `chapter2_region_detection/docs/`，采用带日期时间且不覆盖旧交接的
文件名；若同时维护一个 latest 索引，只能在新交接完成并校验后更新索引。写完后必须重读、
检查格式、计算 SHA256，并把路径和哈希写入当前状态。压缩后的新窗口必须先阅读最新交接
文档，再进行实时复核；交接中的 PID、进度和资源信息只能作为线索，不能替代实时检查。

## 四、每个子任务的强制派发模板

每次派发至少包含以下内容：

1. **最终目标关系**：本任务对应 Table 1、Table 2、Table 3、图或公共门禁中的哪一项；
2. **任务书核对**：方法身份、数据 split、seeds、ticks、预算、奖励、冻结输入和禁止项；
3. **任务目标**：本次必须产出什么，哪些内容明确不在本次范围；
4. **详细方案与设计**：输入、输出、代码 commit、环境、命令、并发策略、恢复策略；
5. **风险控制**：无覆盖、无删除、无 test 泄漏、无在线调用、唯一 writer、资源门；
6. **验收标准**：文件、数量、SHA、manifest、eligibility、测试结果和退出码；
7. **完成后的动作**：先报告主窗口、由主窗口审核和备份，再安排下一阶段。

  证据并由主窗口审核，禁止子代理自行选择较宽松解释。
